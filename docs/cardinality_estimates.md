# Cardinality estimates vs actual row counts

Generated by `python tests/opt_cardinality_table.py`; do not edit by hand.
The estimator is `optimizer/stats.py`; the harness is `optimizer/cardinality_report.py`.

Every number compares the estimator's row count for a plan node with the row count the
reference evaluator returns for that node's subtree. The error measure is the **q-error**,
max(estimate / actual, actual / estimate) with both counts raised to at least 1 row:
1.00 is exact, and 2.00 means off by a factor of two in either direction.

## 1. Where the estimator is right, and where it is wrong

`tests/opt_stats_workload.py` has 1,000 events, 100 users and 300 clicks. Each column was
generated to meet or to break one assumption of the estimator, and each query tests one rule.
The table shows each query's root node.

Where the data meets the estimator's assumptions (14 queries), the median q-error is 1.03 and the worst is 1.43: uniform_equality estimates 10 rows against 7, which is sampling noise. Where the data breaks an assumption (7 queries), the median is 6.67 and the worst 20.00.
The failures are systematic, and each has a known cause:

* **Skew** (`z` is Zipf-distributed). Equality assumes every value is equally common, so it under-estimates the most frequent value by 12.6x and over-estimates the rarest by 6.7x. A join on skewed keys on both sides is 4.1x too low, because the frequent values meet each other far more often than uniformity predicts. The fix is a most-common-values list or a histogram in the catalog; Contract §6 provides neither, so it would be a request to Person A.
* **Correlation** (`b` always equals `a`). AND multiplies selectivities, so `a = 7 AND b = 7` is 19.6x too low, and GROUP BY a, b multiplies distinct counts, which is 20.0x too high. Fixing this needs multi-column statistics.
* **No statistics to use.** A range on a string column can't be interpolated, and a HAVING predicate reads an aggregate the catalog knows nothing about; both fall back to System R's 1/3 (q-errors 1.46 and 1.67).

Every other query whose data meets the assumptions (foreign-key and filtered-dimension joins,
LEFT joins, IS NULL, OR, NOT, date ranges, two-sided ranges, grouped aggregates over a filter)
is within 1.16x.

* `five_way_join_in_a_bad_order`: four joins, each a little off, and the errors multiply.

* `forced_cross_product`: a cross product multiplies the errors of its inputs: two of the five nations are in AMERICA (1.25 expected), and three employees work in a department with a budget over 500 (2.1 expected).
